## 前置

P2 必须全绿。P4 不新建数据结构，它全部建立在 P2 的 `Update` 链上：

```
Entry::upd ──▶ [Update(txnid=7, ts=30)] ──▶ [Update(txnid=5, ts=20)] ──▶ nullptr
                      链头最新
```

P2 的可见性规则只有一条：`txnid <= reader && start_ts <= read_ts`。
它回答不了真正的问题，这就是 P4 存在的理由。

## T4.1 事务状态机与快照（3 项）

### 为什么「比大小」不够

```
时刻   T1                T2                T3
      A.begin()  ─────────────────────────────▶
                        B.begin()
                                          B.commit()
      A.get(k)  ←──── 这里必须看不到 B 的写
```

如果只判 `u->txnid <= A.id`，而 B 的 id 比 A 小（B 开得早但提交晚），
A 就会读到 B 未提交的数据 —— 脏读。所以必须记「A 开始时谁还活着」。

WT 的做法（`src/include/txn.h` 的 `WT_TXN_SNAPSHOT`）：

```
snap_min = 开始时最小的活跃 txn id
snap_max = 开始时最大的已分配 txn id + 1
snapshot = 开始时活跃的 txn id 列表
```

### visible() 的判定顺序

```
1. u->txnid == reader.id              → true     （读自己的写）
2. u->txnid 仍在活跃集合               → false    （别人没提交）
3. u->txnid >= reader.snap_max        → false    （begin 之后才开的）
4. u->txnid ∈ reader.snapshot         → false    （begin 时还活着）
5. u->start_ts > reader.read_ts       → false    （时间戳太新）
6. 否则                                → true
```

**顺序不能换**。第 1 条必须在第 2 条前面：自己的 txnid 也在活跃集合里，
不特判就永远读不到自己刚写的值。这是这一项最常见的 bug。

### rollback：精确摘链

回滚不是「把链头置 nullptr」。链上可能有别的事务的版本：

```
回滚前： [7/txnA] → [5/txnA] → [3/txnB] → [1/base]
回滚 A： 摘掉 7 和 5，保留 3 和 1
```

所以 `Txn.writes` 要记 `(key, Update*)`，回滚时：

1. descend 到 key 所在叶子；
2. 在 `Entry::upd` 链（或 insert 节点的链）上找这个 `Update*` 的**前驱**；
3. 前驱跳过它（`prev->next = cur->next`），释放 cur；
4. 如果这个键本来就不在磁盘镜像里（是 insert 节点），且链被摘空，
   节点也要删掉、`ninserts--`。否则回滚后还能扫到一个空壳键。

## T4.2 写写冲突（1 项）

规则（本版，先写者赢）：

```
put(k) 时看链头：
  链头存在 && 链头的 txnid 属于「另一个未提交事务」 → S_ROLLBACK
```

真 WT 更客气：把后来者挂到冲突队列上，等对方 commit/rollback 再重试
（`WT_TXN_OP` + `txn->mod`）。本版直接让后来者重试，够暴露语义。

`TxnSession::put` 的顺序很重要：**先检查冲突，再挂链**。反过来会让
失败的事务污染链。

## T4.3 History Store（1 项）

### 为什么必须有

一条 update 链不能无限长。但「删掉老版本」会让还在跑的旧快照读到错值：

```
读者 A 的快照在 ts=10
链： [ts=30 v3] → [ts=20 v2] → [ts=10 v1]
如果 eviction 判断「ts=10 已经没人需要」就删了 v1，A 立刻读错。
```

所以判据必须是「**所有**活跃读者都看不到」：

```
oldest_active = min(活跃事务的 read_ts)
ts < oldest_active 的版本 → 可以挪进 HS 或丢弃
```

### HS 的读写

```c
hs.insert(key, update)              // 同一 key 按 start_ts 降序保存
hs.read(key, read_ts, out, found)   // 找 start_ts <= read_ts 的最新一个
hs.evict_older_than(oldest_ts)      // 清掉更老的
```

真 WT 的 HS 是一棵独立的 B-Tree 文件（`WiredTigerHS.wt`），key 是
`(key, start_ts)` 的复合键；本版是内存 `map<Key, vector<Update>>`，
接口语义一致。

## T4.4 Rollback to Stable（1 项）

稳定点（stable timestamp）之前的数据是「所有副本都能看到」的公共历史。
恢复时只能保证到稳定点，之后的东西必须**一致地丢弃**，否则会出现
「A 节点有、B 节点没有」的分裂。

```c
rollback_to_stable(bt, stable_ts);
// 所有 start_ts > stable_ts 的 Update 都要被摘掉
// 摘完之后如果链空了，回落到 base（磁盘镜像里的值）
```

真 WT 还要处理 prepared 事务和 HS 里的版本；本版只处理主链。

## T4.5 WAL 与崩溃恢复（3 项）

### 规则

```
写路径：  日志 append + fsync  →  改内存（update 链）  →  （checkpoint 时）写数据页
```

顺序不能反：先改内存再写日志，崩溃后就丢了（内存里的修改没有落盘）。

### 记录格式（本版）

```
[u8 type][varint key_len][key][varint val_len][val]
type: LOG_PUT=1 / LOG_REMOVE=2 / LOG_COMMIT=3
```

真 WT 的记录头更复杂（`src/include/log.h:311`）：

```
u32 len | u32 checksum | u8 flags | payload
```

并且有 `LOG_ALIGN=128` 对齐、`LSN = (file << 32) | offset`、
首块是 `WT_LOG_DESC{magic, version, allocsize}`。本版砍掉这些，
只保留「先日志后数据」这个核心不变量。

### 恢复

```c
log.replay(bt);   // 顺序扫，PUT → bt.put，REMOVE → bt.remove
```

**必须容忍尾部半截记录**：崩溃时最后一条可能只写了一半。
判断依据是「解析出的长度 > 剩余字节」→ 停止重放，返回成功，不报错。
把这种情况当错误处理，会导致「越崩溃越起不来」。

测试是怎么模拟崩溃的：

```cpp
Btree *bt = new Btree();      // 故意不 delete：析构会 checkpoint
bt->put(...); log.append(...);
// 到这里"断电"：数据文件删掉，日志保留
```
